# 领域资料

智慧交通、电网巡检和算力项目在当地保留原始数据，平台只交换需求基线、环境说明、数据摘要、系统版本与适用声明、以及签名验收结果。

## 数据边界

* 外部主体使用不含真实身份信息的引用编号（如 `PARTNER-TH`、`BKK-DRDC-2026-09-001`）。
* 交换时间采用带偏移量的 ISO 8601 字符串（服务端以 UTC 记录）。
* 原始材料（出行记录、车牌、音视频、抓包等）只保存在当地受控存储，平台内只保存受控引用编号与 64 位十六进制 `sha256` 摘要。
* 写入请求经入口递归扫描：出现 `raw`、`raw_data`、`payload`、`records`、`samples`、`video`、`plate` 等原始数据字段名时直接以 `422 raw_data_rejected` 拒收，`sample_count` 一类聚合字段不受影响。
* 需求基线、环境说明在登记时由服务端对规范化 JSON 计算摘要，验收结论对规范化结论体（项目、里程碑、轮次、版本、逐项结果、判定、时间）计算签名摘要。

## 角色

| 角色 | 权限 |
| --- | --- |
| `institution`（当地机构） | 登记需求基线、数据摘要、现场环境说明；提出/同意指标；创建里程碑；查看本项目全部记录 |
| `supplier`（供应方） | 登记系统版本与适用声明；提出/同意指标；创建里程碑；开启轮次、登记证据摘要、提交结论 |
| `administrator`（管理者） | 登记参与方与项目；查看全部项目与组合视图；不代替双方做业务判定 |

## 四阶段分离

每个项目只能属于一个阶段：`demo`（展品）、`pilot`（试点）、`deployment`（部署）、`acceptance`（正式验收）。`GET /v1/overview` 组合视图按四个桶分列项目及其最新轮次状态，使一次展会演示不会被误报成可交付项目；正式验收结论只产生于 `acceptance` 阶段项目中走完完整流程的轮次。

## 验收规则

1. **先约定指标，后提交结论。** 指标由机构或供应方任一方提出（提出即提出方同意），另一方通过 `POST /v1/metrics/{id}/agree` 同意；全部指标双方同意后，该里程碑的轮次才允许提交结论，否则返回 `409 metric_not_agreed`。
2. **轮次状态机。** `open → passed/failed`，由逐项指标按 `>=, <=, >, <, =` 与阈值自动判定。失败后原轮次冻结（不能补证据、不能改判），重测必须在同一里程碑另开新一轮，历史轮次全部保留。
3. **版本升级失效。** 供应方登记新系统版本时，该项目下所有 `open` 轮次立即转为 `invalidated` 并记录失效时间与致因版本；已结束的 `passed/failed` 轮次不受影响。被失效轮次同样只能另开轮次重验。
4. **证据可见性。** 证据摘要、轮次详情、项目摘要、版本与基线只对项目的机构方、供应方及管理者可见；不相关参与方得到 `403`，列表与组合视图也不包含他方项目。
5. **基准版本绑定。** 每一轮开启时绑定一个已登记的系统版本，结论签名中包含该版本号，保证结果可追溯到具体软件状态。

`contracts/entities.json` 中的字段名称属于稳定接口约定，运行时数据文件位置由 `DATABASE_PATH` 决定。
